# 分层

> 一句话：**domain 不认识 orchestration，orchestration 不认识平台。**
> 这条规则由 `ops/lint-layers.py` 强制，不靠自觉。

## 三层

| 层 | 职责 | 模块 | 允许依赖 |
|---|---|---|---|
| **domain** | 纯规则：怎么分段、怎么拼 prompt、怎么算情绪 | `delivery` `pacing` `prompt` `intent` `textsim` `vec` `memory_score` `mood_domain` `followup_domain` `memory_common` | domain / infra |
| **orchestration** | 编排：一轮对话、命令、调度、引擎门面 | `engine` `runner` `commands` `runtime` `introspect` `chat` `chat_turn` `tool_loop` `scheduler` `proactive` `learn` `review` `memory` … | domain / infra / 同层 |
| **infra** | 基础设施：路径、配置、文件、时钟、数据库 | `paths` `config` `files` `kernel/*` | 不依赖业务 |

上层文档里的 `[domain]` / `[orchestration]` 就是这层标记，写在每个模块的 docstring 第一行。

## 规则

1. **domain 不得 import orchestration。**
   否则纯规则会绑上会话状态和 IO，单测就得起半个系统。
2. **adapters 只走门面。**
   允许 `engine` / `runner` / `commands` / `delivery`；禁止 `chat` / `chat_turn` / `tool_loop`。
3. **plugins 只 import `app_core` 的公开模块**（现状保留，逐步收窄）。
4. **kernel 不反向依赖业务包。**

## 怎么查

```bash
python ops/lint-layers.py      # 20 秒，纯 AST，无依赖
```

反向验证过：给 `pacing.py` 加一行 `from app_core import runner`，lint 立即 FAIL；
删掉恢复 PASS。它不会「永远绿」。

## 新模块放哪层

1. 只做计算、不读写数据库/文件、不知道「一轮对话」？→ **domain**
2. 需要串多个模块、读写状态、响应一次事件？→ **orchestration**
3. 只提供路径/配置/IO 原语？→ **infra**

拿不准时先放 orchestration——domain 的边界越窄越好守。

## 为什么不物理搬家

按层拆目录（`core/domain/`、`core/orchestration/`）会一次改掉所有 import，
而收益只是「看起来更整齐」。现在用 docstring 标记 + lint 规则固定方向，
等真的出现第二个消费者或第二个通道，再决定要不要搬。
