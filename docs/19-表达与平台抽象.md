# 19 · 表达与平台抽象

> 2026-11-15。起因：给 QQ 加「发语音」时只能写成「先产文字 → 事后转语音 → 发出去」，
> 用户指出这是打补丁，并且「以后画个画」会重复同样的补丁；再加一句「QQ 只是适配层」。
> 本文是把这两件事合并成一个结构问题来处理。

## 1 问题：形式是「附加字段」，不是「数据」

现在的三个结构体都在用「主内容 + 若干可选字段」表达形式：

```
InboundMessage(text, images, file)      # 三种形式 → 三个字段
OutboundMessage(chunks, images)         # 两种形式 → 两个字段
Turn(texts, images, file)               # 又是三个字段
```

后果：

- 加「语音」→ 三个类各加字段，或在 `text` 里塞 `[语音]` 前缀（已经这么干了）
- 加「画画」→ 同上再来一遍
- 「这句用说的」这种**形式意图**无处存放，只能靠事后规则猜

## 2 数据模型：Part

```python
@dataclass(frozen=True)
class Part:
    form: str        # text | image | voice | file | drawing
    content: str     # 文本内容，或文件路径
    meta: dict       # 时长、画风、尺寸、MIME、转写置信度……
```

入站、出站、中间态**同一个类型**。形式是数据，所以：

- 入站语音 = `Part("voice", "转写文本")`，不再有 `[语音]` 前缀
- 出站语音 = `Part("voice", "/tmp/v.silk")`
- 「这句用说的」= 两条 Part，形式不同

## 3 通道协议：能力声明 + 自动降级

目前 `Channel` 是三个写死的方法（send_text / send_image / typing）。加一种形式就要改协议——
这正是「换平台要重写」的原因之一。

```python
class Channel(Protocol):
    forms: set[str]          # {"text", "image", "voice"} —— 这个平台支持什么

    async def send(self, session: str, part: Part) -> bool: ...
    async def typing(self, session: str, on: bool) -> None: ...
```

**降级是协议的一部分**：平台不支持某个 form 时，由 `plan.render(parts, channel.forms)` 决定
退化成什么（voice → text，drawing → image）。这样「换平台」不需要改业务代码，只需要写一个 adapter。

## 4 适配层结构

现在 `QQChannel` 活在 `plugins/chat/__init__.py`（390 行的插件里），入站解析也是。
平台代码和业务逻辑混在一起，是「换平台要重写 300 行」的直接原因。

```
app_core/            # 完全不 import nonebot（lint 已强制）
  message.py         # Part / Inbound / Outbound
  channel.py         # Channel 协议 + 降级规则
adapters/
  qq/
    __init__.py      # QQChannel：出站原语
    inbound.py       # event 字段 → InboundMessage（含语音/图片下载转码）
  console/
  fake/
plugins/
  chat/__init__.py   # 只做桥接：event → InboundMessage → engine → 出站
```

判据：**新增一个平台 = 新增一个 `adapters/<name>/` 目录**，不碰 `app_core` 和 `plugins`。

## 5 画画

DeepSeek 没有图像生成接口（2026-11-15 核对 70 页文档，`vision` 是看图不是画图）。
走 provider 抽象，先接智谱 CogView：

```python
# app_core/image_provider.py（仿 embed_provider）
async def generate(prompt: str, size: str = "1024x1024") -> Path | None
```

`Part("drawing", path)` 与 `Part("image", path)` 的区别：前者是**生成**，后者是**已有图**。
对通道来说都是发图，所以 adapter 不需要区分。

## 6 迁移路径

| 步 | 内容 | 行为变化 | 风险 |
|---|---|---|---|
| 1 | 加 `Part` 类型，三个结构体加 `parts` 字段与旧字段并存，全部 form=text | 无 | 低 |
| 2 | 出站语音/图片改为构造 Part，删 `_speak_later` 那种事后转换 | 无 | 中 |
| 3 | `Channel` 收敛成 `send(part)`，三个 adapter 改 | 无 | 中（QQ 发送链路） |
| 4 | 删旧字段；入站 `[语音]` 前缀换成 `Part("voice")` | 有（历史渲染变了） | 中 |

每步一个 commit，跑 721 + 基线 + 真机验证。

## 7 不做什么

- **不做插件系统**：形式只有 4-5 种，不需要动态注册。
- **不做多平台并行**：现在只有 QQ + console，抽象是为了「将来加平台不用重写」，
  不是为了「同时接 5 个平台」。
- **不让模型直接构造 Part**：模型仍只输出文本，形式由规则层决定；等结构稳定后再考虑
  「模型声明形式」（那需要 prompt 协议，会动基线）。
