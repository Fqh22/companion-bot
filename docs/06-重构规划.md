# 重构规划：模块化单体 + 纵向切片

> 目标不是「拆得更小」，是**让每个功能的修改只影响自己**。
> 不做微服务、不重写、不在同一批里改行为和搬文件。

## 一、目标与非目标

**目标**

- app_core 从「42 个平铺模块」收敛成 6–8 个**纵向功能包**。
- 每个包内部：纯 domain → service → ports → adapters。
- plugins 只做 QQ IO 和组装，不写业务。
- 保持 core.* / plugins 现有调用方式不变（门面兼容）。
- 每一步都能上线、能回滚、全量测试保持绿。

**非目标**

- 不拆微服务、不拆独立仓库、不换语言。
- 不重写 prompt / 人格 / 记忆算法。
- 不在搬文件的同时改数据库 schema。
- 不为了「分层」给每个函数写 Protocol。

## 三、依赖规则（用 lint 强制）

    plugins → services → domain
                  ↑   ↓
                ports ← adapters

- kernel：只 import 标准库（settings 可 import yaml）。
- domain：不 import sqlite3 / httpx / nonebot / adapters。
- service：只 import domain + ports，不 import adapters。
- adapters：实现 ports，可以 import 外部库。
- plugins：只 import 门面（plugins.chat.core），不 import 子模块。
- 现有 CORE_API 清单继续用；新增/删除接口必须先登记。

新增 ops/lint-layers.py：AST 扫 import，违反规则直接 FAIL，接入 verify/CI。

## 五、分阶段计划

### P0 · 安全网（2–3 天）

- 记录基线：628 离线 / 225 全链路 / 81 agentd / 48 面板；关键路径耗时。
- 补 characterization 用例：召回 top-k、cleanup/supersede/restore、流式扣句、mood 衰减、followup 状态、scheduler 补跑。
- 新增 ops/lint-layers.py，先把规则跑成 WARN，再逐步转 FAIL。
- 产出：本文件 + 依赖图。

**Gate**：全绿，行为零变化。

### P1 · kernel（3–4 天）

- Settings：从 DEFAULTS + config.yaml 构建 dataclass；config.load() 保留兼容。
- Clock：SystemClock / FakeClock；先接入 memory、mood、scheduler、followup。
- db.py：连接工厂、WAL、busy timeout、事务上下文；**不换 schema**。
- types.py：先放 MemoryItem / Message，不急着全量替换 dict。

**Gate**：628 全绿；时间相关用例可以用 FakeClock 跑。

### P2 · memory 纵切（4–6 天）

1. memory/domain.py：时间/重要性/重复降权、阈值、排序；recall 调它。
2. memory/store_sqlite.py：CRUD、状态、range_key、清理/取代/恢复。
3. memory/index.py：矩阵、BM25、实体图缓存与失效。
4. memory/embedding.py：HTTP + 缓存。
5. memory/service.py：Memory 门面；app_core.memory.Memory 保持可用。

**Gate**：50 条真实 query 的 top-5 与重构前完全一致；cleanup/supersede 用例全绿。

### P3 · chat 纵切（4–6 天）

- chat/domain.py：Turn、分段、建议裁剪、风格规则。
- chat/service.py：四段流水线；ChatCore 只保留组装和公共接口。
- 插件仍调 core.reply，不动。

**Gate**：流式/超时/重试/工具循环用例全绿；218 全链路不变。

### P4 · mood / proactive / scheduling（4–6 天）

- mood 纯动力学 + store；proactive 只留 policy + sources；scheduling 合并 followup/remind/scheduler。
- clock 注入，替换 time.time() 和 datetime.now() 的关键路径。

**Gate**：gate/pick_topic/due/补跑/冷却用例全绿；主动消息行为不变。

### P5 · knowledge / integrations（可选，3–4 天）

- 只做目录归并和 facade，不改内容生成逻辑。
- 优先级低于 P0–P4；不做也不影响主链路。

### P6 · schema 迁移 + typed settings（3–4 天）

- schema_version 表 + 有序迁移脚本；去掉运行时的 ALTER TABLE ... except pass。
- 配置面板 schema 直接来自 Settings，DEFAULTS 只保留兼容导出。
- **放在最后**：这是唯一会动数据的阶段。

### P7 · 收尾（2 天）

- 删除兼容包装（确认无调用）、更新 docs、CORE_API 重新登记。
- 跑六件套 + 面板测试 + 一次云端恢复演练。

## 七、验收标准（整个重构）

- 依赖 lint 零 FAIL；domain 无 IO import。
- 628 / 225 / 81 / 48 全绿；云端 6/6。
- 召回 top-5、清理/取代、流式分段、主动消息 gate 与重构前一致。
- core.* 和 7 个插件不需要改调用方式。
- 没有新增运行时依赖；没有行为变化（除明确的 bug 修复）。
- 单文件行数：service/domain 目标 < 400 行；ChatCore < 300 行。

## 八、风险与回滚

| 风险 | 处理 |
|---|---|
| 召回排序静默变化 | 50 条真实 query 对比 top-5；不一致就回滚该步 |
| 全局 config / 路径难注入 | 先做兼容包装，逐步替换，不一次性删 |
| SQLite 事务/并发退化 | store 保留 WAL + busy timeout；单连接每操作 |
| 测试是「改出来的」 | 先写 characterization，再搬代码 |
| 大改期间线上出问题 | 每阶段独立 commit + 备份 + 可回滚；不全量重写 |
| 时间不够 | 只做 P0–P2，chat 保持原样也仍然可用 |

## 九、不做什么

- 不拆微服务、不拆仓库、不换框架。
- 不做通用 Repository / DI 框架 / 事件溯源。
- 不在搬文件时改 prompt、改阈值、改 schema。
- 不为了行数拆包；包的数量由「变化原因」决定。
- 不删除仍在做决策的影子实验（BM25、实体图）——先做决定，再删代码。

## 十、决策点

1. **P2 之后是否继续 P3？** 看 memory 重构后是否真的更敢改；否则停在 P2。
2. **P6 是否做？** 只有准备多实例/多人维护时才值得；单用户可以先不做。
3. **knowledge 包是否合并？** 如果 P5 没有真实需求，保持平铺更省事。

---

**一句话**：先把「变化最频繁、SRP 最差」的 memory 纵切出来，kernel 只做时钟/配置/连接三件小事；chat 第二；其余按需。大改不等于重写。
