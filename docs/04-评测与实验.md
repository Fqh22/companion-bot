# 04 · 评测与实验

> **L4 · 怎么知道改好了。** 定义见 [01](01-定义与决策.md) · 系统见 [02](02-系统与扩展.md) ·
> 状态：稳定（2026-11-16 重写，合并旧 15 / 16 / 17 / 18）。**设计稿与已实测结论分开标注。**

## 1 · 原则

- **先证伪「召回有用」**，不要先优化召回。真实陪伴流量里只有约 3.4% 的消息需要回忆
  （RealCompanion，2026-10），瓶颈是「什么时候不检索」，不是「怎么检索」。
- **依赖型 / 非依赖型分开统计**，不报池化分数。池化增益 96% 会落在根本不需要记忆的探针上。
- 每条探针**跑 3 次报分布**，固定模型版本与温度；judge prompt 的 **sha256 冻结**并写进
  `run_manifest`（不冻结时两次跑分不可比，实测有 0.62 vs 0.79 的先例）。
- **影子实验必须有截止时间，到期转正或移除**（01 §6）；只用于不可逆或有争议的改动。
- 数字标日期；厂商自报基准不与第三方实测混用。

## 2 · 记忆评测探针（设计）

`ops/memory-eval.py`，15 条 × 3 类，每类 5 条，每条带冻结的 `t_q`（提问时刻）。

| 类 | A 关召回 | B 当前 | C | D |
|---|---|---|---|---|
| 时间推理 | 只留近期 | 当前 | 注入归一化后的事实 | 注入**未**归一化的原话 |
| 知识更新 | 只留近期 | 当前 | 注入更新后的事实 | — |
| 弃答 | 只留近期 | 当前 | C′：注入相关但不含答案的干扰事实 | 显式空证据 + 允许说不知道 |

- 弃答通过 = 没有具体答案 + 明确表示记不清 / 没听他说过；给出具体但错误的答案 = 失败。
- 知识更新只看最终值，允许提及旧值（否则会把「模型自己选对了」和「存储层没裁决」混为一谈）。
- D 组用于归因：D 也败 → 阅读/推理问题；D 成而 B 败 → 抽取或召回问题。

指标：命中且用上 / 召回但没用 / 误召回 / **重复告知率**（用户有没有重复告诉它同一件事，
最贴近「它记得我」）。`memory_trace` 早期只记 `query / ids / trace`；批次 2 已补
`injected[].score`、`injected[].deleted`、`probe_id`、`t_recall_ms`，并把**原始余弦分**
从 `memory.recall()` 经 `MemoryPort` 传到 trace（调制后的 `final` 是排序分，不当相似度报）。
`deleted` 恒为 false：非 active 记录在 `_docs_by_ids` 已被过滤。仍待补（随阶段 2 引导式埋点）：

```json
{"extracted":[{"text":"","normalized_time":""}],"superseded":[],
 "t_extract_ms":0,"t_gen_ms":0}
```

阶段 1 是 15 条合成探针 + 冻结 fixture（库状态、clock、memories），顺带评抽取质量；
阶段 2 是**引导式埋点**：真实对话里主动说出带相对时间且计划后续更新的事实，
记录埋点时间与依赖目标，1–2 周后回问。不等自然积累（5.8 天攒的 679 条大多是孤立事实）。

## 3 · 已跑出的结论（2026-11-14 云端实测）

| 结论 | 数字 |
|---|---|
| 弃答规则有效，但被粗判吃掉 | 断言编造 2 → 0，求证 3 → 4，弃答 0 → 1；A 组弃答 2 → 5 |
| judge 分不清「断言」与「求证」之前，任何规则改动都不该下结论 | 规则冻结在 `ops/fixtures/judge_abstain.py` |
| seed 没模拟软删会给出错误结论 | 修正后 B 旧值 4/5 → **0/5**，B 新值 4/5 → **5/5**：**软删是有效的** |
| prompt 只能治「不换算」，治不了「算错」 | 时间推理 1/5 → 4/5 → **5/5**（最后一步把日期算术交给 `timenorm.normalize`） |
| fixture 的期望值本身算错（t1 应为 2026-11-18，写成 11-19） | 修正后 B 4/5、D 3/5，之前低估了 |
| 三次重复推翻了单次结论 | C′ 组不是 0/5，是 **2/15**，且集中在 a1（同一输入 2 次编造、1 次求证） |
| 黄金基线覆盖缺口 | `c26-memory-hit` / `c27-knowledge` 的 `memory_blocks: 0`（哈希假向量过不了 `recall_min_score=0.35`）；评测侧已改用真实 embedding，云端自检通过、生产库未触碰 |

残留：C′ 的 a1 仍是**不稳定编造点**（干扰项与问题主题高度相关）。
**「有召回时仍编造」这条曾被认为存在的问题，是 judge 误判，不是系统缺陷。**

**2026-11-22 复查时间锚点**：同一句「明天」有三处独立的「今天」——历史注入时的消息
时间、批量总结的来源时间、主动跟进的入库时间；任何一处用错都会复述旧的「明天」或换成
一个错日期。`ops/test-dates.py` 用固定时间点逐条回归（跨午夜 / 跨年 / 延迟总结 / 无来源）。

## 4 · 现实层（状态、感知、痕迹）

四层不要混成一个筐：事实（跨会话断言）/ 状态（今天在弄什么）/ 感知（天气、时间）/ 痕迹（日记、周报）。
`PerceptionPort.read(topic)` 返回 `fact(as_of, source, ttl, confidence)` 或 `unknown(reason)`；
契约显式失败，prompt 静默降级，失败不编。

注入预算：现实上下文 **120 字封顶**（clock 30 / perception 40 / task 50，task ≤2 条）；
距上次 >6h 才带 clock；天气缓存 30–60 分钟；`profile_slow` 30 天；突变提醒每周 ≤1 次。
验收（v1 尚未开始）：每周抽 10 条人工标「正确 / 过时 / 编造」盯编造率，
clock 延迟均值增量 <1%，先跑一周做基线。

## 5 · 纠正分诊

**当场识别、后台判断、三类去处**：本人待办置 done / 外人纠正写进本人 fact 与全局 corrections /
既非纠正也非待办则丢弃。判断 schema：`is_correction` / `kind(fact|behavior|none)` /
`claim` / `confidence` / `why`；判据 `fact 且 confidence ≥0.7 且 claim 非空 → 记忆`，
失败 3 次进 `data/corrections_unverified.jsonl`，24h 相似度兜底。

时序：不同步写记忆（矛盾检测要问一次模型，会吃掉整轮预算），放回合后台 `asyncio.create_task`。
幂等用 `range_key = "corr:" + sha1(归一化 claim)[:16]`。验收 5 条（未跑）。
落地文件：`data/corrections_pending.jsonl`、`data/corrections_unverified.jsonl`、
`data/review_state.json`、`corrections.md`。

## 9 · 记忆存储格式（设计稿，未排期）

状态：**设计稿**。2026-11-16 记录，未开始实现，不要当成已完成来引用。

### 9.1 要解决什么

`docs/01-定义与决策.md` §3 说「SQLite 里的记忆不算可携带」。现在 `ops/export-subject.py`
是导出口，存储本身仍是 `livingmemory.db`：不能 diff、不能进 git、换实现要迁移。

### 9.2 不做什么

- 不换记忆引擎（不引入 Mem0 / Zep），也不做「文件即数据库、每次召回逐行解析」。
- 不追求「每轮都读文件」——那会把 12ms 的召回拖到几百 ms，属于拿体验换格式。

### 9.3 设计：文件是真相源，SQLite 是派生索引

```text
qqbot-data/memory/
  facts/2026-11-16.jsonl        # 原子事实：每行一条，带 id / 时间 / 来源 / 置信度
  docs/2026-11-16--slug.md      # 文档正文（learn/notes 已经是这个形状）
  profile/self_profile.md       # 画像（已有）
  corrections.md / curious.md   # 清单（已有）
  vectors/                      # 向量 sidecar（二进制，不进 git，可重建）
  index.sqlite                  # 派生索引：随时可从上面重建
```

- **写路径**：先写文件（append + fsync），再更新索引；索引失败不回滚文件（可重建）。
- **读路径**：只读 `index.sqlite`，保持现在的召回延迟；索引落后由 refresh 任务补偿。
- **可携带**：facts / docs / profile 全是文本，`export-subject` 退化成「打包这几个目录」。
- **重建**：`ops/rebuild.py` 扫文件重建索引，是唯一的重建入口。

### 9.4 分三步迁移

1. **双写**：写入同时落文件与 SQLite，读仍走 SQLite；用重建脚本校验一致率（目标 100%）。
2. **切换读取**：索引缺条目时回退文件；观察一周召回条数与延迟。
3. **删旧表**：确认没有回退需求后 drop，保留 `ops/rebuild.py`。

### 9.5 判据与门槛

- 五问（`docs/01-定义与决策.md` §5）：连续性（重建后还是它）、可携带（文本可 diff）、
  可审计（每行带来源）、降级（索引坏了回退文件）、不污染事实（表达层不写 facts）。
- 门槛：召回 p95 延迟 ≤ 现在的 2 倍；11MB 生产库重建 ≤ 10 秒。

### 9.6 风险

- **并发写**：单进程 + 文件锁；崩溃时以「已 fsync 的行」为准。
- **向量**：二进制不进 git，sidecar 丢失可重新 embedding（132 条，成本可忽略）。
- **回滚**：双写阶段随时可切回纯 SQLite。



## 10 · TurnContext（设计稿，未排期）

状态：**设计稿**。2026-11-16 记录；低成本版已落地，完整版未做。

### 10.1 现状

ChatTurnMixin 通过 self 访问 ChatCore 的 19 个成员（history / memory_port /
build_messages / complete_* / _run_tools …）。B2 拆分后这层耦合没有护栏：
ChatCore 改名或删成员，只有跑起来才炸。

**已落地的低成本版**：chat_turn.py 的 TURN_DEPS 显式列出这 19 个名字，
ops/lint-plugins.py 的 check_turn_deps 做两件事——新增 self.xxx 未登记 → FAIL；
TURN_DEPS 里的成员在 ChatCore（含三个 Mixin）上找不到 → FAIL。
反例验证过：把 self.seg_max 换成 self.nope_dep，lint 立刻红。

### 10.2 完整版是什么

TurnPipeline 独立类 + TurnContext dataclass：把 19 个依赖作为字段显式传入，
turn 流水线不再继承 ChatCore。收益是可单测（不用造一个完整 ChatCore）、依赖可 mock。

### 10.3 为什么现在不做

- 收益是**可测性**，而 turn 流程已被 735 条离线 + 39 条 prompt 基线 + 288 条全链路覆盖；
- 成本是 40+ 处 diff（19 个字段 + 12 个方法签名），review 成本高于收益；
- 判据：出现「第三个通道」或「turn 需要独立单测」时再做，否则 TURN_DEPS + lint 已覆盖
  「依赖静默漂移」这个真实风险。
