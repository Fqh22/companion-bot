# 04 · 评测与实验

> **L4 · 怎么知道改好了。** 定义见 [01](01-定义与决策.md) · 系统见 [02](02-系统与扩展.md) ·
> 状态：稳定（2026-11-16 重写，合并旧 15 / 16 / 17 / 18）。**设计稿与已实测结论分开标注。**

## 1 · 原则

- **先证伪「召回有用」**，不要先优化召回。真实陪伴流量里只有约 3.4% 的消息需要回忆
  （RealCompanion，2026-10），瓶颈是「什么时候不检索」，不是「怎么检索」。
- **依赖型 / 非依赖型分开统计**，不报池化分数。池化增益 96% 会落在根本不需要记忆的探针上。
- 每条探针**跑 3 次报分布**，固定模型版本与温度；judge prompt 的 **sha256 冻结**并写进
  `run_manifest`（不冻结时两次跑分不可比，实测有 0.62 vs 0.79 的先例）。
- **影子实验必须有截止时间，到期转正或移除**（01 §6）；只用于不可逆或有争议的改动。
- 数字标日期；厂商自报基准不与第三方实测混用。

## 2 · 记忆评测探针（设计）

`ops/memory-eval.py`，15 条 × 3 类，每类 5 条，每条带冻结的 `t_q`（提问时刻）。

| 类 | A 关召回 | B 当前 | C | D |
|---|---|---|---|---|
| 时间推理 | 只留近期 | 当前 | 注入归一化后的事实 | 注入**未**归一化的原话 |
| 知识更新 | 只留近期 | 当前 | 注入更新后的事实 | — |
| 弃答 | 只留近期 | 当前 | C′：注入相关但不含答案的干扰事实 | 显式空证据 + 允许说不知道 |

- 弃答通过 = 没有具体答案 + 明确表示记不清 / 没听他说过；给出具体但错误的答案 = 失败。
- 知识更新只看最终值，允许提及旧值（否则会把「模型自己选对了」和「存储层没裁决」混为一谈）。
- D 组用于归因：D 也败 → 阅读/推理问题；D 成而 B 败 → 抽取或召回问题。

指标：命中且用上 / 召回但没用 / 误召回 / **重复告知率**（用户有没有重复告诉它同一件事，
最贴近「它记得我」）。`memory_trace` 目前只记 `query / ids / trace`，至少需补：

```json
{"turn_id":"","probe_id":"","injected":[{"id":"","score":0,"deleted":false,"text":""}],
 "extracted":[{"text":"","normalized_time":""}],"superseded":[],
 "t_extract_ms":0,"t_recall_ms":0,"t_gen_ms":0}
```

阶段 1 是 15 条合成探针 + 冻结 fixture（库状态、clock、memories），顺带评抽取质量；
阶段 2 是**引导式埋点**：真实对话里主动说出带相对时间且计划后续更新的事实，
记录埋点时间与依赖目标，1–2 周后回问。不等自然积累（5.8 天攒的 679 条大多是孤立事实）。

## 3 · 已跑出的结论（2026-11-14 云端实测）

| 结论 | 数字 |
|---|---|
| 弃答规则有效，但被粗判吃掉 | 断言编造 2 → 0，求证 3 → 4，弃答 0 → 1；A 组弃答 2 → 5 |
| judge 分不清「断言」与「求证」之前，任何规则改动都不该下结论 | 规则冻结在 `ops/fixtures/judge_abstain.py` |
| seed 没模拟软删会给出错误结论 | 修正后 B 旧值 4/5 → **0/5**，B 新值 4/5 → **5/5**：**软删是有效的** |
| prompt 只能治「不换算」，治不了「算错」 | 时间推理 1/5 → 4/5 → **5/5**（最后一步把日期算术交给 `timenorm.normalize`） |
| fixture 的期望值本身算错（t1 应为 2026-11-18，写成 11-19） | 修正后 B 4/5、D 3/5，之前低估了 |
| 三次重复推翻了单次结论 | C′ 组不是 0/5，是 **2/15**，且集中在 a1（同一输入 2 次编造、1 次求证） |
| 黄金基线覆盖缺口 | `c26-memory-hit` / `c27-knowledge` 的 `memory_blocks: 0`（哈希假向量过不了 `recall_min_score=0.35`）；评测侧已改用真实 embedding，云端自检通过、生产库未触碰 |

残留：C′ 的 a1 仍是**不稳定编造点**（干扰项与问题主题高度相关）。
**「有召回时仍编造」这条曾被认为存在的问题，是 judge 误判，不是系统缺陷。**

## 4 · 现实层（状态、感知、痕迹）

四层不要混成一个筐：事实（跨会话断言）/ 状态（今天在弄什么）/ 感知（天气、时间）/ 痕迹（日记、周报）。
`PerceptionPort.read(topic)` 返回 `fact(as_of, source, ttl, confidence)` 或 `unknown(reason)`；
契约显式失败，prompt 静默降级，失败不编。

注入预算：现实上下文 **120 字封顶**（clock 30 / perception 40 / task 50，task ≤2 条）；
距上次 >6h 才带 clock；天气缓存 30–60 分钟；`profile_slow` 30 天；突变提醒每周 ≤1 次。
验收（v1 尚未开始）：每周抽 10 条人工标「正确 / 过时 / 编造」盯编造率，
clock 延迟均值增量 <1%，先跑一周做基线。

## 5 · 纠正分诊

**当场识别、后台判断、三类去处**：本人待办置 done / 外人纠正写进本人 fact 与全局 corrections /
既非纠正也非待办则丢弃。判断 schema：`is_correction` / `kind(fact|behavior|none)` /
`claim` / `confidence` / `why`；判据 `fact 且 confidence ≥0.7 且 claim 非空 → 记忆`，
失败 3 次进 `data/corrections_unverified.jsonl`，24h 相似度兜底。

时序：不同步写记忆（矛盾检测要问一次模型，会吃掉整轮预算），放回合后台 `asyncio.create_task`。
幂等用 `range_key = "corr:" + sha1(归一化 claim)[:16]`。验收 5 条（未跑）。
落地文件：`data/corrections_pending.jsonl`、`data/corrections_unverified.jsonl`、
`data/review_state.json`、`corrections.md`。
