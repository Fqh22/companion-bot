# 18 · 记忆评测：先证伪「召回有用」

> 2026-11-14　·　状态：设计稿，未开始跑
> 背景：LongMemEval（ICLR 2025）五项能力、RealCompanion 的消融结论（BM25 检索 10 条 1.426，不给记忆 1.431）、
> 以及本地 BM25 影子数据（333 次 / 2.97，人工抽检否决）。

## 1 · 要回答的三个问题

1. **记忆进了 prompt，回复有没有变好？**（不是 hit@5）
2. **变差的比例有多大？**（召回了过期/互斥事实，导致回复更错）
3. **瓶颈在哪一段？**（抽取 / 召回 / 阅读推理）

## 2 · 探针设计（15 条 × 3 类）

每类 5 条。每条必须带 `t_q`（提问时刻，冻结），否则「下周三」本身无解。

| 类 | 例子 | A 组（关召回） | B 组（当前召回） | C 组 | D 组 |
|---|---|---|---|---|---|
| 时间推理 | 「下周三的面试是哪天？」 | 只留近期 | 当前 | 注入归一化后的事实 | **注入未经归一化的原话** |
| 知识更新 | 「我搬走了吗？」 | 只留近期 | 当前 | 注入更新后的事实 | — |
| 弃答 | 「我上次说的那个项目叫什么？」（他没说过） | 只留近期 | 当前 | **C′：注入一条相关但不含答案的干扰事实** | 显式空证据 + 允许说不知道 |

- **弃答类没有「正确事实」可注入**，C 组换成 C′：测「记忆在场时模型是否仍编造」。
- **时间推理加 D 组**：D 也败 → 阅读/推理问题；D 成而 B 败 → 抽取或召回问题。这是 A/B/C 分辨不出来的归因。
- **知识更新只看最终答案**：官方 judge 容忍答案里提到旧值，只要最终给出的是新值就算对。按「两条互斥事实一起进 prompt」直接判失败，会把「软删没触发但模型自己选对了」和「存储层根本没裁决」混为一件事。

## 3 · 判分规则（必须先冻结）

- 每条探针跑 **3 次**，报告分布而不是均值；固定模型版本与温度。
- judge prompt 的 **sha256 冻结**，写进结果文件——不冻结的 judge 会让两次跑分不可比（实测有 0.62 vs 0.79 的先例）。
- 弃答类通过条件：**没有给出具体答案 + 明确表示记不清/没听他说过**。给出一个具体但错误的答案 = 失败。
- 知识更新通过条件：最终值正确，允许提及旧值。

## 4 · 指标

| 指标 | 定义 |
|---|---|
| 依赖型 / 非依赖型 | **分开统计**，不报池化分数（RealCompanion 的教训） |
| 命中且用上 | 回复引用了正确事实 |
| 召回但没用 | 记忆在 prompt 里，回复没用到 |
| 误召回 | 过期/互斥事实进了 prompt 且影响了回复 |
| **重复告知率** | 用户有没有重复告诉它同一件事——最贴近「它记得我」的朴素指标 |

## 5 · 需要先补的埋点（memory_trace）

现在只记 `query / ids / trace`，不够归因。至少补：

```json
{"turn_id": "", "probe_id": "", "injected": [{"id": "", "score": 0, "deleted": false, "text": ""}],
 "extracted": [{"text": "", "normalized_time": ""}], "superseded": [],
 "t_extract_ms": 0, "t_recall_ms": 0, "t_gen_ms": 0}
```

只记召回轨迹、不记「注入的是哪条、带不带软删标记」，回答不了「召回了错的」。

## 6 · 阶段划分

- **阶段 1（现在）**：15 条合成探针 + 冻结 fixture（库状态、clock、memories）。
  同时把 `memory_trace` 的入库事实文本、时间归一化结果、软删动作记下来——
  **这一步顺带就把「抽取质量」评了**，不必等阶段 2。
- **阶段 2**：真实探针。不等自然积累（5.8 天攒的 679 条大多是无依赖关系的孤立事实），
  改成**引导式埋点**：在真实对话里主动说出带相对时间、且计划后续更新的事实，记录埋点时间与依赖目标，1–2 周后回问。

## 6.5 · 已知覆盖缺口（2026-11-14 实测）

`c26-memory-hit` / `c27-knowledge` 在 36 条基线里**没有记忆块、没有知识块**：

```
c26-memory-hit memory_blocks: 0 []
c27-knowledge  memory_blocks: 0 []
```

原因：黄金工具用的是哈希假向量，过不了 `recall_min_score=0.35`（`memory.py:68`），
召回为空。所以这两条 case 名字叫 memory-hit / knowledge，实际只覆盖了「查询文本没变」。
**记忆注入路径的字节级覆盖是 0。**

评测侧已改用真实 embedding（`ops/memory-eval.py` 借 keys.json），
2026-11-14 云端自检通过：召回 1 条、trace 字段齐全、隔离根、生产库未触碰。

## 6.6 · 第一次规则迭代：5/5 → 4/5 是假象，2 → 0 才是真的

2026-11-14 加了弃答规则（记忆里没有就说记不清），用 v0 判定（回复里出现干扰项名称 = 编造）：

| 组 | 改前 | 改后 |
|---|---|---|
| 弃答 C′（注入干扰） | 5/5 | 4/5 |

看起来没效果。换成 v1 判定（把「断言编造」和「求证式提及」分开）：

| 组 | 改前 | 改后 |
|---|---|---|
| C′ assert（断言编造） | **2** | **0** |
| C′ confirm（求证） | 3 | 4 |
| C′ abstain（明确弃答） | 0 | 1 |
| A 组 abstain | 2 | **5** |

**结论反转**：规则有效，但被粗判吃掉了。
典型对比例子：
- 改前「Atlas？你之前提过的那个副业项目。」→ assert
- 改后「Atlas 吧，… 还有个记账工具，你说的哪个？」→ confirm

v0 把两种都算失败，所以「5/5 → 4/5」实际上是「2 条断言 + 3 条求证 → 0 条断言 + 4 条求证 + 1 条弃答」。

**教训**：judge 分不清之前，任何规则改动都不该下结论。规则本身冻结在 `ops/fixtures/judge_abstain.py`，
hash 进 run_manifest（`judge` 字段）。

残留问题：B 组仍有 1 条 assert（有召回时编造），真实存在，未解决。

## 6.7 · 评测自身的两个缺陷（都会给出错误结论）

**缺陷一：judge 太粗**（§6.6 已记）。v0 把「断言编造」和「求证」算一类，
导致「规则 5/5→4/5」看起来无效，实际断言从 2 降到 0。

**缺陷二：seed 没模拟软删**。知识更新类的 5 条 case 预置了新旧两条事实，
但 `add_document` 全写成 `active`——两条都进召回，于是「B 组旧值 4/5」，
看起来像「矛盾检测没生效」。

修正：seed 时对 `status=superseded` 的旧事实调用
`memory.supersede(old_id, new_id, "评测：知识更新")`，再跑：

| 组 | 修正前（两条都 active） | 修正后（真软删） |
|---|---|---|
| 更新 B 旧值 | 4/5 | **0/5** |
| 更新 B 新值 | 4/5 | **5/5** |
| 更新 C 旧值 | 3/5 | 1/5 |

**软删是有效的**。之前那个「旧值 4/5」是评测设置的问题，不是系统的。
u3 的回复还顺带证明了弃答规则在「记忆不全」时也生效：
「这个我真不知道。我记着的只有你今天新养了只年糕，之前有几只没跟我说过。」

## 6.8 · 时间推理：1/5 → 5/5 的三步

| 阶段 | B 组答对 | 做法 |
|---|---|---|
| 初始 | 1/5 | 时间行只说「算明天/下周几以此为准」 |
| 要求换算 | 4/5 | 改成「先按上面的日期换算成 MM-DD 再说」 |
| 写入归一化 | **5/5** | `timenorm.normalize`：明天/后天/下周X/月底 → 绝对日期 |

关键判断：**prompt 只能治「不换算」，治不了「算错」**。中间那步之后模型开始输出日期，
但会算错（把 11-18 说成下周三——其实它是对的，是 fixture 写错了，见下）。
最终把日期算术从模型手里拿走，交给 Python。

**第四个评测缺陷**：fixture 里 t1 的 `normalized` 写成 `2026-11-19`，
但 2026-11-14 是周六、下周三是 **11-18**。修正后重判，B 4/5、D 3/5（之前低估了）。
这是「fixture 的期望值本身算错」——比 judge 和 seed 更隐蔽，因为没人会怀疑标准答案。

## 6.9 · judge v2：提到干扰项 ≠ 把它当答案

v1 仍有误判。a5 问「我养的那只狗叫什么」，回复是：

> 我这儿只记着你那两只猫，团子和年糕。狗的名字真没印象，你说过吗？

v1 看到「团子」就判 assert（编造），但这是**排除**——它明确说「狗的名字真没印象」。
v2 加一档 `abstain_mentioned`：先说不知道、再提到干扰项 = 排除，不算编造。

重判后：

| 组 | v1 assert | v2 assert |
|---|---|---|
| 改前 B | 1 | 1 |
| 改后 B | **0** | **0**（那条其实是 abstain_mentioned） |
| 改后 C′ | 0 | 0 |

**「有召回时仍编造」这条残留问题不存在**——是判定把它算错了。
真实结论：弃答规则在 A/B/C 三组全部有效（C′ assert 2→0、A abstain 2→5）。

## 6.10 · 三次重复：单次结论被推翻了一部分

弃答类 × 3 次（15 次/组）：

| 组 | assert | confirm | abstain / mentioned | none |
|---|---|---|---|---|
| A（关召回） | 0 | 0 | 13 | 2 |
| B（正常召回） | **0** | 0 | 10 | 5 |
| C′（注入干扰） | **2** | 5 | 8 | 0 |

**C′ 组不是 0。** 单次跑出来是 0/5，三次重复后是 2/15，而且集中在 a1：
`{'assert': 2, 'confirm': 1}`——**同一个输入，2 次编造、1 次求证**。

这推翻了 §6.9 的「assert 2→0」：
- 规则确实把「每次都编」降成了「偶尔编」（2/15 ≈ 13%）
- 但 a1 的「干扰项与问题主题高度相关」（问『那个项目叫什么』，注入『他提过 Atlas 的副业项目』）仍是不稳定的编造点

**这就是为什么必须 3 次重复**：单次的 0/5 是抽样运气，不是能力。

## 7 · 不做的事

- 不因为「想试试」就上混合检索：BM25 重合度 2.97 已低于转正阈值，但人工抽检否决——
  这证伪的是「重合度」这个代理指标（它测差异，不测互补增益），不是「这次恰好没转正」。
- 不把「向量阈值调高」当成「窄而准」的迁移：followup 的可靠来自**两层窄**——
  候选池窄（只跟进未完成事项）+ 匹配窄（2-gram ≥0.7）。
  可迁移的是「结构化路由先缩小候选池」，不是「把全库检索调严」。
